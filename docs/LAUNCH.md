# Публичный запуск KaleaDoSkill

Статус: сайт и документы подготовлены в рабочей облачной среде. Домен, VPS и внешний публичный адрес ещё не предоставлены. Форма заявок и платежи отключены до настройки соответствующих интеграций.

## Что сделать владельцу

1. Создать аккаунт в российском облаке, например Timeweb Cloud (https://timeweb.cloud/) или Selectel (https://selectel.ru/). Покупка сервера и регистрация домена оформляются на владельца: здесь не настроены его аккаунт и платёжный доступ.
2. Выбрать VPS в российском дата-центре, Ubuntu 24.04 LTS, 2 vCPU, 4 ГБ RAM, SSD от 30 ГБ, публичный IPv4. Отдельную БД покупать не требуется. Выбирать актуальную цену в панели; ранее указанный бюджет — ориентир, а не проверенный тариф.
3. Зарегистрировать выбранный пользователем домен `kaleadoskill.ru`. Доступность при регистрации ещё не проверена.
4. Предоставить имя домена, IPv4 сервера и имя пользователя SSH. Пароли, приватные SSH-ключи, токен бота и банковские ключи в чат не отправлять.
5. Для доступа к серверу добавить публичный SSH-ключ из `/workspace/deployment-access/kaleadoskill-deploy.pub` через панель провайдера. Приватный ключ остаётся в рабочей среде вне репозитория; его не передавать и не коммитить. При утрате текущей среды понадобится выпустить новый ключ и заменить доступ в панели. Отпечаток SSH-ключа самого сервера получить через консоль провайдера для проверки первого подключения.
6. Создать DNS A-запись для корня домена (`@` либо пустое имя в зависимости от панели) с IPv4 сервера. Не добавлять AAAA, если IPv6 не настроен. Дождаться появления записи. Для начала используем один основной домен; www подключается отдельно.

После предоставления сервера помощник сможет загрузить проект, настроить запуск и HTTPS, проверить главную страницу, документы и вход, подготовить бэкап. Если SSH из облачной среды запрещён платформой, потребуется терминал провайдера либо другой поддерживаемый доступ; доступность ещё не проверена.

## Комплект для технического размещения

В репозитории есть `Dockerfile`, `deploy/compose.yaml`, `deploy/Caddyfile`, `deploy/production.env.example` и скрипт SQLite-бэкапа. Production-сборка Next.js проверена непосредственно на Node 24. Статус проверки контейнера и HTTPS указан в `VALIDATION.md`; внешний выпуск сертификата до предоставления домена/сервера не проверен.

На целевом VPS установить Docker Engine и Compose по актуальной официальной инструкции для Ubuntu: https://docs.docker.com/engine/install/ubuntu/. Использовать штатную проверку подписей пакетов. До включения firewall разрешить SSH с нужного адреса; для сайта открыть TCP 80 и 443. Приложение не публикует порт 3000 наружу.

Файлы проекта разместить в `/srv/kaleadoskill`. Из `deploy/production.env.example` создать `/srv/kaleadoskill.env` с правами 0600. Заполнить SITE_DOMAIN. Пароль админки (от 16 символов) и session secret (от 32 символов) сгенерировать на сервере и сохранить в этом файле, не выводя значения в отчёт и не сохраняя в Git. Задать токен и chat ID только при готовой интеграции. Оставить LEADS_ENABLED=false до проверки обработки данных и доставки.

Из корня проекта:

```sh
docker compose --env-file /srv/kaleadoskill.env -f deploy/compose.yaml up -d --build
docker compose --env-file /srv/kaleadoskill.env -f deploy/compose.yaml ps
```

Caddy автоматически запрашивает сертификат для указанного домена при корректном DNS и доступных портах. Данные сертификатов и SQLite сохраняются в Docker volumes. Не выполнять `docker compose down -v`: эта команда удаляет постоянные volumes. При перезапуске хостинга контейнеры запускаются автоматически.

Все сохранённые в текущей среде изменения контента нужно перенести отдельной проверенной копией SQLite через `scripts/backup.mjs`; один исходный код не переносит админские правки. В частности, номер телефона в текущей БД уже указан. При миграции сначала остановить только целевой сервис и сохранить его текущую БД, затем заменить проверенным бэкапом и восстановить владельца файлов (uid 1000).

## Проверка после размещения

- Главная, `/legal/offer`, `/legal/privacy`, `/legal/consent` возвращают HTTP 200 по HTTPS.
- Сертификат действителен, HTTP перенаправляется на HTTPS.
- Официальный Telegram, дополнительный Telegram и телефон +7 952 672 7722 указаны корректно.
- ADMIN_PASSWORD и ADMIN_SESSION_SECRET включают защищённый вход; публичный admin API без сессии возвращает 401.
- SITE_URL формируется из SITE_DOMAIN и используется при сборке и запуске; canonical, OG, robots и sitemap относятся к настоящему домену.
- Отсутствие заявок/токена не приводит к ложному сообщению «отправлено».
- После подключения бота согласованная тестовая заявка действительно приходит в нужный закрытый чат. Только после этого включается форма.
- Документы проверены владельцем/специалистом, дата публичного размещения указана фактически. Согласованное сопровождение — 6 месяцев и бесплатные недельные продления при активности, поддержка после начала работы — 1 месяц.
- SQLite-бэкап читается и имеет `PRAGMA integrity_check = ok`; копия хранится отдельно от диска сайта.

Наличие текстов не доказывает выполнение этих требований. Telegram Bot API и банковские продукты фактически ещё не подключены.
